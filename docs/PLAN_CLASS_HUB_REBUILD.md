## 0. 무엇을 건드리고 무엇을 안 건드리나

| | |
|---|---|
| **안 건드림** | 자산화(HWP/HML/OCR) · 문제은행 · 인쇄(ExamPaperView) · 시험지 출제 검색 |
| **다시 만듦** | 그 위의 **학습 운영 층** — 반·과제·채점·숙달·리포트 |

자산화와 인쇄는 이 프로그램에서 제일 오래 다듬은 부분이고 잘 돈다. 그건 **자산**이다.
문제는 그 위에 얹힌 운영 층이 **필요할 때마다 하나씩 붙여** 만들어졌다는 것.

## 1. 지금 무엇이 잘못됐나 (실측)

### (1) 학생 하나를 보려면 메뉴 6개를 돌아야 한다

```
반 관리 · 학생 관리 · 채점하기 · 수동 채점 입력 · 학생 진단 · 학생 성적
· 클리닉시험지 · 학교별 리포트 · 진단 종합 리포트 · 수업 홈
```

같은 학생 이야기가 열 군데에 흩어져 있다. 매쓰홀릭은 **반 하나를 열면 그 안에 전부** 있다.

### (2) 채점 라인이 두 개다

| 라인 | 저장 | 쓰는 화면 |
|---|---|---|
| A | `diagnostics.sessions` + `items` | 수동 입력 |
| B | `diagnostics.print_sessions` + `session_results` | QR · 엑셀 · 이미지 채점 |

**같은 사실("이 학생이 이 문제를 맞았나")을 두 곳에 다르게 쓴다.**
그래서 리포트마다 한쪽만 보이고, 집계할 때마다 합치는 코드를 또 짠다.
(마이그레이션 `20260605_001` 이 숙달 계산만 겨우 합쳐 놨다 — 근본 해결이 아니다)

### (3) "과제" 개념이 없다

우리에겐 **시험지**만 있다. 매쓰홀릭은 시험지와 별개로 **과제**가 있고, 그게 운영의 단위다.
- 기간(시작~마감)이 있다
- 대상 학생이 있다
- 제출/미제출이 보인다
- **네 갈래로 만든다**: 단원 · 오답 · 취약 · 유형

우리는 시험지를 만들어 인쇄해 주면 끝이라, **누가 언제까지 뭘 해야 하는지**가 시스템에 없다.

### (4) 진단 스키마가 API에 안 열려 있다

`diagnostics` 가 PostgREST 노출 목록에 없어 **채점 라인 전체가 런타임에 죽는다.**
아직 안 써서 드러나지 않았을 뿐. 이걸 켜지 않으면 무엇을 만들어도 안 돈다.

## 2. 목표 구조 — 반 하나가 스파인

```
반 목록
 └ 반 열기  ──────────────────────────────────────────────
    학생 | 과제 | 채점 | 숙달 | 이력 | 설정
      │      │      │      │      │
      │      │      │      │      └ 주차별 추이 (스냅샷)
      │      │      │      └ 단원 × 난이도 매트릭스
      │      │      └ QR·엑셀·수동 한 라인
      │      └ 단원 / 오답 / 취약 / 유형  4갈래
      └ 진행도 · 정답률 · 최근 학습
```

매쓰홀릭은 16탭이지만 **우리는 6탭이면 된다.** 레벨업·연산·메쓰톡·문자 같은 건 우리 사업에 없다.

### 왜 반 중심인가
학원은 **반 단위로 운영한다.** "3학년 A반 오늘 뭐 하지"가 실제 질문이고,
"김태한 학생의 확률 숙달도"는 그 다음 질문이다. 지금 우리 IA 는 순서가 거꾸로다.

## 3. 데이터 — 세 가지만 정리하면 된다

### (1) 채점을 한 라인으로

**남길 것: `print_sessions` + `session_results`** (B라인)
- `problem_id` 로 실제 문제를 가리킨다 → 오답·취약 과제의 재료가 된다
- QR·엑셀·이미지 채점이 이미 여기 쓴다

**흡수할 것: `sessions` + `items`** (A라인)
- `mathsecr_code` 만 있고 `problem_id` 가 없다 → "무슨 문제를 틀렸는지" 모른다
- 수동 입력 화면을 B라인에 쓰도록 바꾸면 A라인은 읽기 전용 과거 기록이 된다

> ★ 기존 데이터는 **지우지 않는다.** 읽는 경로만 B로 통일하고, A는 과거 이력으로 남긴다.
>   (items 2,746건 · session_results 1,658건 — 둘 다 살아있는 기록이다)

### (2) 과제 테이블 신설

```
assignments            id · institute_id · class_id · title
                       kind: unit | wrong | weak | type      ← 네 갈래
                       exam_id (생성된 시험지)
                       starts_at · due_at · created_by
assignment_students    assignment_id · student_id · session_id(채점 세션) · status
```

**과제 = 시험지 + 대상 + 기간.** 시험지는 이미 만들 수 있으니, 감싸는 층만 있으면 된다.

### (3) 숙달 스냅샷

`student_node_status` 는 **현재 상태만** 있어 추이 차트를 못 만든다.
주 1회 스냅샷을 쌓는다.

```
student_node_snapshots  student_id · week_of · alpha_cnt · beta_cnt · gamma_cnt · unknown_cnt
```

행이 작다(학생 × 주). 매쓰홀릭 유형이력의 GREEN/RED/GRAY 꺾은선이 이걸로 나온다.

### ✅ 단계 1 완료 (2026-09-02) — 읽는 곳 전수 통일

읽는 경로를 B(print_sessions + session_results) 하나로 모았다. 실측 효과:

| | 전 | 후 |
|---|---|---|
| 보이는 학생 | 44명 | **57명** |
| 보이는 채점 세션 | 111개 | **181개** |

옮기다 드러난 것 (전부 이미 나 있던 사고):
- **부분점수 유실** — 이관 때 `partial:획득/만점` 이 하나도 안 넘어왔다. 실제 부분점수 258문항이
  만점/0점으로 뭉개져 있었다. A 원본에서 `awarded_points`/`max_points` 로 복구(2,721건 전수 일치).
- **자사관 난이도 집계가 항상 0** — A `items.difficulty` 가 2,746건 전부 NULL 이었다.
  이제 `classifications.difficulty`(1~10) 로 계산. 버킷 상 7~10 / 중 5~6 / 하 1~4.
- **학생 위키 이력 중복** — A·B 를 둘 다 찍어 같은 시험이 두 줄씩(110줄) 나왔다.
- **새 공유 링크 미리보기 폴백** — OG 레이아웃이 옛 토큰만 봐서 제목·점수가 안 떴다.

일부러 안 옮긴 것: **담임 수동 진단 입력 폼**(`prescription/lib/queries.ts`).
A 세션 111개가 **전부 EX(시험 채점)** 이라 이 폼으로 만든 세션은 0건 — 죽은 경로다.
쓰기 시작하면 리포트에 안 나오므로, 그때 B 스키마로 옮긴다(코드에 경고 주석).

★ 설계에서 가장 중요한 결정: **제출 여부를 assignment_students 에 안 박는다.**
  "이 학생이 이 시험지를 쳤나" 의 사실은 채점 세션에 이미 있다. 같은 사실을 두 곳에
  쓰면 반드시 어긋난다 — 채점 라인이 둘로 갈려 리포트마다 한쪽만 보이던 게 정확히
  그 사고였다. 그래서 제출 현황은 **매번 채점 세션에서 계산**하고, `status` 컬럼은
  면제(excused) 같은 **사람의 판단**만 적는다.

실데이터 검증 (중3 엄궁중 5명):
- `25-3-1-F 엄궁중 수학` → 5/5 제출, 정답률 50·65·65·85·90 (평균 71%)
- `25-3-1-F 엄궁중 수학 유사1` → **4/5 제출, 1명 미제출**, 평균 73%
검증용 과제는 확인 후 삭제.

**학생 id 에 FK 를 안 걸었다.** users.id 일 수도 roster_students.id 일 수도 있어서
(명단으로 채점하다 승격하면 기록이 옛 id 에 남는다) 두 테이블을 동시에 가리키는
FK 는 만들 수 없다. 앱의 신원 병합으로 푼다.
